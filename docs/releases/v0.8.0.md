# HorusTrace v0.8.0 — Deployed Authority & Least-Privilege Reconciliation

HorusTrace v0.8 connects the effective-authority model built in v0.5–v0.7 to
deployment and IAM evidence while preserving the project's static-first, local-first
trust boundary.

The new question is:

> What authority does this deployed agent identity have, how does that differ from
> supported source-observed authority, and does it comply with repository policy?

## Deployment Evidence v1

v0.8 introduces a normalized JSON/YAML evidence contract for:

- deployed workloads and explicit agent bindings;
- runtime service-account identities;
- IAM roles and permissions;
- project/folder/organization inheritance;
- conditional IAM bindings;
- role-to-permission expansion evidence.

The contract is deliberately provider-neutral at the schema boundary. The first
implemented authority resolver is GCP-focused.

HorusTrace does not contact Google Cloud while evaluating this evidence. Evidence can
be produced by a controlled enterprise export process and passed to CI as an ordinary
input artifact.

## Workload identity resolution

Explicit workload-to-agent bindings are resolved to deployed identities. GCP service
accounts are canonicalized before IAM correlation.

HorusTrace does not use fuzzy name similarity to decide that an application agent and
a cloud workload are the same principal. Ambiguous or invalid identity evidence stays
unresolved.

## Deployed authority

For an explicitly bound workload identity, HorusTrace reconstructs supported deployed
authority from supplied IAM evidence:

- direct and inherited roles;
- expanded predefined/custom-role permissions where supplied;
- resource scopes;
- inheritance provenance;
- conditional permissions kept separate from unconditional authority.

Unknown role expansion or IAM-condition applicability remains unresolved.

## Required vs deployed reconciliation

`horustrace reconcile` compares:

1. supported source-observed authority;
2. deployed IAM authority; and
3. repository Authority Contract constraints.

Example:

```bash
horustrace reconcile ./agent-app \
  --deployment-evidence ./evidence/prod.yaml \
  --format json
```

Agent reconciliation status is one of:

- `aligned`
- `excess_authority`
- `missing_authority`
- `mixed`
- `unresolved`

HorusTrace only calls authority excess when the corresponding required dimension has
a supported baseline. Missing intended-authority evidence is not treated as proof that
all deployed authority is unnecessary.

## Deployment authority drift

A prior evidence snapshot can be supplied to make deployment analysis change-aware:

```bash
horustrace reconcile ./agent-app \
  --deployment-evidence ./evidence/head.yaml \
  --baseline-deployment-evidence ./evidence/base.yaml \
  --fail-on-deployment-regression
```

The delta reports:

- roles/permissions added or removed;
- introduced/resolved excess authority;
- unresolved-authority regression or improvement;
- selected trust-boundary crossings such as secret access, IAM mutation and
  destructive mutation.

## Authority Contract correlation

Deployed identities, IAM roles and permissions can be evaluated against the same
repository-local Authority Contract used for source authority.

Conditional conflicts are reported as unresolved unless their applicability is
established by the supplied evidence.

## CI gates

v0.8 adds opt-in gates:

```text
--fail-on-excess-authority
--fail-on-deployed-policy-violation
--fail-on-deployment-regression
```

The first-party GitHub Action supports `mode: reconcile` with equivalent inputs.

## Validation boundary

The v0.8 implementation includes controlled aligned and expanded deployment fixtures,
unit tests across evidence loading, identity mapping, deployed IAM resolution,
reconciliation, policy evaluation and drift, plus CLI/Action integration checks.

The frozen public repository corpus does not contain normalized deployment evidence,
so its historical static metrics are not evidence of deployed-authority correctness.

v0.8 remains deliberately conservative:

- no target application import or execution;
- no agent or MCP server launch;
- no production credential testing;
- no cloud API calls by the reconciler;
- no claim that a discovered permission was exercised;
- all deployed-authority outputs retain `runtime_effectiveness: not_verified`.

Authenticated provider acquisition can be added later as an optional evidence producer
without changing the core reconciliation model.
