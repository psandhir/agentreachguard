# HorusTrace v0.6.0

**Authority Policy & Trust-Boundary Enforcement**

HorusTrace v0.6.0 turns the effective-authority model introduced in v0.5 into an
enforceable repository-local security contract.

The progression is:

```text
v0.5
What can this agent actually reach and do?

v0.6
Is that authority allowed, and did this pull request make it worse?
```

The release adds Authority Contract v1, trust-boundary classification, policy-aware
security deltas and CI gating, source-addressable explanations, and an evidence-backed
taxonomy for unresolved MCP references.

The static/local-first trust boundary remains unchanged. HorusTrace does not import or
execute target applications, start MCP servers, contact configured endpoints, fetch live
cloud IAM, or claim runtime effectiveness from static configuration.

## Authority Contract v1

A repository can now express expected authority directly in
`horustrace.manifest.yaml` under `policy.authority`.

Supported contract dimensions include:

- capabilities;
- identities;
- resources;
- destinations;
- IAM roles;
- permissions;
- OAuth scopes;
- MCP servers;
- approval requirements;
- per-server MCP tool allow/deny scope.

Example:

```yaml
version: 1

agents:
  - name: support-agent

    policy:
      authority:
        allow:
          capabilities:
            - data.read
            - data.write
          identities:
            - support-bot
          destinations:
            - https://support.example.com/*
          mcp_servers:
            - github

        deny:
          capabilities:
            - process.execute
          iam_roles:
            - roles/owner

        require_approval_for:
          - external.write

        mcp_tools:
          - server: github
            allow:
              - issues_read
              - issues_comment
            deny:
              - repo_delete
```

Authority Contract v1 extends the existing manifest rather than introducing a second
policy language or policy server.

## Contract evaluation: compliant, violation, unresolved

Each effective-authority relationship is evaluated against the contract with three
explicit outcomes:

- `compliant` — supported static evidence satisfies the relevant contract;
- `violation` — supported static evidence conflicts with the contract;
- `unresolved` — available evidence cannot prove either outcome.

Unknown evidence is neither pass nor failure.

This matters for dimensions such as identity, approval state and dynamic MCP tool scope,
where absence of static evidence must not be converted into a clean result.

Contract results use stable identifiers while intentionally excluding observed sensitive
values and checkout-specific paths from fingerprints.

All runtime-effectiveness fields remain:

```text
not_verified
```

## Trust Boundary Classification v1

v0.6 classifies effective-authority relationships across five boundary families.

### Mutation

Examples include:

- no mutation;
- local/session mutation;
- internal mutation with unspecified persistence;
- persistent internal mutation;
- external side effect;
- destructive mutation;
- security/identity-sensitive mutation;
- unknown.

### Network

Examples include:

- no external network;
- fixed destination;
- provider-constrained destination;
- internet retrieval;
- arbitrary egress.

### Identity

Examples include:

- workload/service identity;
- delegated OAuth authority;
- IAM authority;
- broad privileged authority;
- unknown.

### Control

Examples include:

- mandatory approval;
- guardrail control;
- explicitly no approval;
- unknown.

### MCP scope

Examples include:

- explicit positive allowlist;
- denylist only;
- dynamic scope;
- unknown;
- not applicable.

The classification is evidence-backed and deliberately avoids a numeric risk score.

## Authority Delta v2

`horustrace diff` now projects before/after trust-boundary classifications onto
effective-authority changes.

A changed relationship can therefore explain transitions such as:

```text
mutation:
  no_mutation
  -> external_side_effect

control:
  mandatory_approval
  -> explicitly_no_approval
```

JSON, console and Markdown reports expose boundary crossings separately from generic
authority expansion.

Existing Authority Delta v1 fields remain available with their original meaning.

## Policy-aware pull-request gate

The v0.6 diff surface evaluates Authority Contracts independently in the base and head
revisions.

The policy delta reports:

- base violation count;
- head violation count;
- newly introduced violations;
- resolved violations;
- newly introduced unresolved assessments;
- Authority Contract changes;
- policy weakenings;
- policy strengthenings.

The opt-in CLI gate is:

```bash
horustrace diff BASE..HEAD \
  --repo . \
  --fail-on-policy-violation
```

The first-party GitHub Action exposes the same behavior through:

```yaml
with:
  fail-on-policy-violation: true
```

The policy gate is independent of the existing severity gate.

### Historical policy debt does not fail every PR

A violation already present in the base revision does not fail a pull request merely
because it still exists.

The gate targets newly introduced policy debt.

### Contract weakening is also gated

v0.6 closes an important policy-bypass case.

A pull request cannot make a violation disappear simply by weakening the contract that
defined the boundary.

The gate detects weakening including:

- widening or removing a positive allow constraint;
- removing deny constraints;
- removing approval requirements;
- widening or removing an MCP positive allowlist;
- removing MCP deny entries;
- removing an existing restrictive Authority Contract while the agent remains.

Policy strengthening remains non-failing.

Scope comparison is glob-aware. For example:

```text
data.* -> data.read
```

is tightening, while:

```text
data.read -> data.*
```

is weakening.

Removing the entire agent is not treated as policy weakening merely because its contract
also disappears.

## Explainability v2

Policy results now carry source-addressable evidence rather than only a reason code.

HorusTrace retains exact manifest locations for supported contract clauses including:

- `allow.<dimension>`;
- `deny.<dimension>`;
- `require_approval_for`;
- `mcp_tools.<server>.allow`;
- `mcp_tools.<server>.deny`.

Each violation or unresolved result can connect:

```text
policy clause
  -> agent
  -> effective-authority relationship
  -> tool or MCP server
  -> observed capability / identity / destination / resource / scope
  -> approval/control evidence
  -> source / ADG evidence
```

Console and Markdown diffs show the policy source and authority source directly.

JSON preserves the structured explanation for downstream tooling.

Explanation data does not participate in stable violation fingerprints.

## MCP unresolved-reference taxonomy v1

The previous notion of an “unbound MCP server” mixed two materially different cases:

```text
a concrete server declaration exists but is not agent-bound

versus

an agent references a server that HorusTrace cannot uniquely resolve
```

v0.6 separates them.

Concrete declarations remain in the existing MCP server inventory.

Unresolved agent references are tracked separately and do not inflate
`Graph.all_mcp_servers()` or trigger server findings as though a concrete server had
been declared.

Current reason codes include:

- `server_not_declared`;
- `declaration_not_agent_bound`;
- `cross_file_reference_unlinked`;
- `ambiguous_multiple_candidates`;
- `dynamic_server_selection`;
- `unsupported_reference_shape`;
- `framework_semantics_unknown`.

Each unresolved observation includes a stable reference ID, reason, resolution class,
candidate declarations where applicable, evidence gaps and a recommendation.

### False-binding correction

v0.6 also fixes an imported-MCP placeholder path where a reference that failed unique
repository resolution could later be marked bound merely because the placeholder still
sat inside an agent object.

Imported references now become effective authority only when a unique static
repository-local declaration is established.

Otherwise they remain unresolved.

### Fifteen previously hidden MCP references

The new MCP taxonomy exposes a separate evidence set:

- concrete unbound declarations: **516**;
- unresolved agent references: **15**;
- total unresolved MCP observations: **531**.

The additional 15 are not new server declarations and should not be described as the
historical 516 count increasing.

Their reasons are:

- 13 `server_not_declared`;
- 1 `ambiguous_multiple_candidates`;

All 15 were manually adjudicated at their pinned repository revisions.

- `evalstate/fast-agent` — 10 references;
- `Klavis-AI/klavis` — 5 references.

The ambiguous FastAgent reference has multiple same-name candidates without sufficient
static scope evidence to select one safely, so it remains unresolved by design.

## Trust-boundary evidence coverage in the frozen study

The v0.6 classifier processed **2,600 effective-authority relationships**.

The study also exposes where public-repository evidence remains sparse.

### Identity

- workload/service identity: **8**;
- unknown: **2,592**.

### Control

- mandatory approval: **83**;
- guardrail control: **87**;
- explicitly no approval: **2**;
- unknown: **2,428**.

### MCP positive scope

Among 117 bound MCP relationships:

- explicit positive allowlist: **8**;
- unknown scope: **109**.

These are not release failures and HorusTrace does not fill the gaps by assumption.
They identify high-leverage future normalization work.

Network classification had zero unknown relationships in the frozen cohort.

## Important Authority Contract study limitation

The frozen public corpus contains **zero repository-local HorusTrace v0.6 Authority
Contracts**.

Therefore the frozen study reports:

- agents with Authority Contract: 0;
- contract relationships evaluated: 0;
- contract violations: 0;
- unresolved contract assessments: 0.

This is **not** evidence that the 90 repositories are compliant.

The public corpus is observational and predates the new policy syntax.

Authority Contract parsing, evaluation, stable identity, weakening detection,
Explainability v2 and policy-gate behavior are instead covered by the project's
regression suite and CI fixtures.

For the complete empirical record, see:

[`docs/research/frozen-90-v0.6.0-baseline.md`](../research/frozen-90-v0.6.0-baseline.md)

## Compatibility

v0.6.0 is additive for existing scan users.

Existing major surfaces remain available:

- `horustrace scan`;
- `horustrace graph`;
- `horustrace security-graph`;
- `horustrace authority`;
- `horustrace diff`;
- `horustrace owasp`;
- `horustrace adapters`;
- AIBOM export;
- JSON and SARIF reporting;
- existing rule identifiers and finding fingerprints.

Notable schema evolution:

- Authority Delta advances to schema v2;
- Authority policy delta advances to schema v2;
- Effective MCP Authority advances to schema v2.

The new fields are additive to the retained v1-compatible semantics described in the
individual module documentation.

The `fail-on-policy-violation` GitHub Action input remains opt-in and defaults to
`false`.

## Static-first safety boundary

HorusTrace still does not:

- import target Python modules;
- execute target code;
- start an agent;
- start an MCP server;
- contact configured MCP endpoints;
- authenticate to production SaaS/cloud systems;
- download live IAM bindings;
- test credentials;
- claim that static authority was exercised at runtime.

Unknown and unresolved evidence remain explicit.
