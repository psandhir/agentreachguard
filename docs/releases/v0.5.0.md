# HorusTrace v0.5.0

HorusTrace v0.5.0 is the largest release since the project was renamed and published as HorusTrace.

Since v0.4.1, the project has accumulated **43 merged pull requests and 266 commits**. The release moves HorusTrace beyond framework-aware static findings toward a more explicit **effective-authority, reachability and attack-path analysis platform for agentic systems**.

The major themes are:

- reconstructing **which agent can reach which tool/MCP server using which identity**;
- proving whether security-relevant flows are actually attributable to an agent;
- separating runtime application behavior from tests, examples, CLI utilities and support code;
- turning authority changes into a first-class pull-request security signal;
- expanding framework coverage without weakening the static/no-execution trust model;
- using a frozen 90-repository public study to drive precision improvements rather than adding broad heuristics.

## Agent Security Graph v1

A new `horustrace security-graph` command exports the versioned **Agent Security Graph (ASG) v1**.

ASG co-locates, in one deterministic document:

- framework-neutral dependency topology;
- effective-authority relationships;
- static data-flow evidence;
- attack paths;
- analysis coverage;
- unresolved evidence.

Repository paths are normalized and the canonical graph digest is stable across checkout locations.

The existing `horustrace graph` ADG export remains available and backward compatible. ASG is an additive higher-level security projection intended to become the common contract for authority delta, attestation, runtime correlation and future language frontends.

## Effective Authority Relationship v1

v0.5 introduces a generic authority model across direct tools and MCP servers.

Each relationship can record:

- effective agent;
- target kind and target name;
- capabilities;
- identity and credential evidence;
- IAM roles/permissions where statically available;
- OAuth scopes;
- approval/guardrail evidence;
- MCP allow/deny tool scope;
- resources;
- network destinations;
- mutation and network semantics;
- explicit resolution state for each dimension;
- unresolved dimensions;
- supporting ADG `INVOKES` evidence;
- stable `authority-v1:` relationship identifiers;
- `runtime_effectiveness: not_verified`.

Missing evidence remains `unknown` or `partially_resolved`; HorusTrace does not fill missing authority dimensions by assumption.

The generic model is exposed through:

```bash
horustrace authority .
horustrace authority . --format json --output effective-authority.json
```

Normal JSON scan output also includes `effective_authority`.

### Authority-aware findings

Several high-value rules now consume effective-authority relationships directly:

- `AGT040` — privileged tool without explicit guardrail/approval;
- `AGT032` — remote MCP server without explicit tool allowlist;
- `NET002` — outbound capability without destination constraint;
- `CAP005` — combined read/write authority.

Linked findings carry the stable `authority_relationship_id` that informed the decision.

Where authority evidence is incomplete, the existing conservative rule fallback remains active rather than suppressing findings or inventing missing context.

## Authority Delta v1

`horustrace diff` now compares effective-authority relationships semantically, not only finding or graph-node changes.

Authority expansion can be attributed to concrete changes such as:

- capability added;
- identity attached or changed;
- IAM role added;
- permission added;
- OAuth scope added;
- approval/control weakened;
- MCP tool scope widened;
- resource added;
- destination added;
- entirely new effective-authority relationship.

For example, a pull request can now explain that:

```text
support-agent -> tool:send_message

Authority expanded:
+ data.write
+ roles/editor
- mandatory approval
+ destination external.example
```

rather than exposing those as unrelated low-level changes.

Authority Delta is available in JSON, console and Markdown output.

## First-class GitHub pull-request security diff

v0.5 adds a change-aware Git security-diff workflow and first-class GitHub Action support.

The diff machinery can compare repository revisions and report:

- introduced/resolved findings;
- ADG changes;
- runtime versus non-runtime finding changes;
- effective-authority expansion;
- contextual Markdown suitable for pull-request summaries.

The GitHub Action uses immutable revision inputs and emits the same Markdown security delta used by the CLI.

This makes HorusTrace useful as a review-time control rather than only a repository scanner.

## Flow attribution and reachability

One of the largest bodies of work since v0.4.1 was improving the answer to:

> Is this data-flow actually reachable through a normalized agent/tool path?

### Provenance-based flow → agent correlation

Static flow attribution now prefers canonical normalized source provenance such as:

- module/function key;
- source path;
- source line;
- import module/alias information.

Cross-file imported tools can be mapped to the correct agent when evidence is unique.

Weak attribution shortcuts were removed:

- no repository-wide simple-name matching;
- no “single agent in repository” shortcut;
- ambiguous multi-agent mappings remain unresolved.

Each flow records its binding basis.

### Execution-context classification

Every supported flow now carries explicit execution context such as:

- `agent_tool`;
- `runtime`;
- `cli`;
- `test`;
- `example`;
- `tutorial`;
- `notebook`;
- `template_generated`;
- `application_support`;
- `unknown`.

The scanner separately records:

- `proven_agent_reachable`;
- `proven_non_agent`;
- `unknown`.

This distinction prevents findings in tests, scripts and repository-maintenance code from being presented as equivalent to agent-reachable runtime behavior.

### Explicit CLI entrypoint evidence

CLI classification now understands static evidence including:

- direct calls under `if __name__ == "__main__"`;
- `[project.scripts]`;
- `[project.gui-scripts]`;
- conservative package-level CLI re-exports.

The execution-context basis is recorded in flow metadata.

### Source-context filtering

A new source-context filtering surface allows users to exclude contexts such as tests from active finding reporting and fail-on evaluation without removing coverage diagnostics.

`--exclude-source-context` and its source-role alias support repeated or comma-separated filters.

Filtering changes reported findings, not scanner coverage. Dynamic or unresolved code inside excluded contexts remains visible as incomplete analysis.

### Inbound runtime entrypoint provenance

Security-relevant flows can now expose bounded reverse-call provenance showing which entrypoints can reach the analyzed helper.

The implementation includes class methods and recognizes evidence such as:

- CLI roots;
- constructors;
- application/runtime roots;
- source-context roots;
- MCP-server lifecycle roots such as `MCPServer.__init__`.

High-cardinality test or CLI entrypoints cannot consume the entire evidence budget before a distinct runtime entrypoint kind is represented.

The candidate search is explicitly bounded and reports truncation rather than implying that all inbound callers have been enumerated.

Importantly, inbound provenance improves explanation without automatically changing agent reachability.

## Static data-flow and attack paths

### Agent tool inputs → sensitive sinks

HorusTrace can now trace normalized agent-tool input parameters into supported security-sensitive sinks.

This creates a stronger bridge between:

```text
agent/tool input
      ↓
static call/data flow
      ↓
sensitive sink
```

rather than treating a sink and an agent capability as unrelated evidence.

### Proven agent flows become supported attack paths

Flows with supported static data-flow evidence and proven agent reachability can be promoted into static-dataflow-backed attack paths.

Potential capability-co-occurrence paths remain distinct from paths backed by supported static flow evidence.

v0.5 therefore preserves the difference between:

- **potential** attack-path combinations; and
- **supported static data-flow** attack paths.

Neither category claims live exploitability.

## MCP authority reconstruction

MCP analysis changed substantially in this release.

### Contextual agent ↔ MCP binding

HorusTrace now reconstructs MCP relationships from framework context rather than merely reporting that an MCP server exists somewhere in a repository.

Supported evidence includes, where statically resolvable:

- imported OpenAI MCP server objects;
- OpenAI agent clone/runtime MCP lists;
- LangGraph / LangChain MCP clients;
- `MultiServerMCPClient(...) -> get_tools() -> agent tools=` paths;
- LangChain `create_agent` MCP authority;
- FastAgent `servers=[...]` references;
- local FastAgent configuration scope.

Only MCP servers statically associated with the effective agent are promoted into that agent's authority.

Unused or ambiguous clients remain unbound.

### Effective MCP authority

MCP authority reconstruction can include:

- effective agent;
- endpoint/destination;
- protocol/transport;
- credential source;
- authentication state;
- configuration-derived identity;
- allow/deny tool scope;
- resource scope;
- filesystem authority for supported stdio server configurations.

The ADG projects supported relationships such as:

- `INVOKES`;
- `USES_IDENTITY`;
- `CONNECTS_TO`;
- `ALLOWS_TOOL`;
- `DENIES_TOOL`;
- `READS_FROM`;
- `WRITES_TO`.

### FastAgent YAML MCP configuration

HorusTrace now parses `fast-agent.yaml` and `fast-agent.yml` MCP definitions, including supported static forms of:

- `mcp.servers.<name>.target`;
- URL targets;
- stdio command shorthand;
- command and args;
- transport;
- protocol metadata;
- header authentication evidence;
- environment-backed credential sources such as `${MCP_TOKEN}`.

Agent `servers=[...]` references are resolved against the nearest enclosing FastAgent config first, falling back to repository-wide uniqueness only when safe.

Duplicate-name ambiguity remains unresolved.

Per-agent FastAgent tool filters are projected onto the effective MCP relationship and intersected with existing server allowlists when both are present.

### MCP gap telemetry

Coverage now records reason-level telemetry for unresolved MCP references and unknown flow reachability.

This makes research and enterprise triage able to distinguish missing evidence, ambiguous evidence, unsupported dynamic configuration and intentionally unresolved runtime behavior.

## New framework coverage

### First-class Pydantic AI / Pydantic AI Harness support

v0.5 adds a first-class static adapter for Pydantic AI and Pydantic AI Harness.

Supported constructs include:

- `Agent(...)`;
- `@agent.tool`;
- `@agent.tool_plain`;
- constructor `tools=`;
- `Tool(...)`;
- `FunctionToolset`;
- toolset decorators/additions;
- combined toolsets;
- approval-required toolsets;
- `requires_approval=True`;
- MCP and MCP toolsets;
- provider-native MCP;
- Harness filesystem capabilities;
- shell/process execution;
- coder capabilities;
- web/browser capabilities;
- sub-agent surfaces;
- sandbox surfaces;
- selected provider-native tools.

Dynamic toolsets and unsupported authority remain explicit coverage gaps.

Pydantic AI normalizes into the existing HorusTrace Agent/Tool/MCP/capability model, so the normal Layers 1–5, policy, authority and attack-path machinery applies.

### First-class FastAgent support

v0.5 adds static support for the decorator-driven FastAgent Python API, including:

- `FastAgent(...)` application instances;
- `@fast.agent`;
- `@fast.custom`;
- workflow decorators including orchestrator, iterative planner, router, chain, parallel, evaluator/optimizer and maker patterns;
- static workflow delegation;
- explicit `function_tools=[...]`;
- uniquely scoped agent-function tools;
- conservative global `@fast.tool` handling;
- `shell=True` process-execution authority;
- `human_input=True` input surfaces;
- static MCP server names and filters.

The initial adapter deliberately surfaced unresolved global tools and MCP references as coverage gaps; later v0.5 work added contextual YAML/MCP authority resolution rather than assuming global reachability.

### Expanded LangGraph semantics

Beyond the v0.4.1 graph-discovery work, v0.5 adds richer LangGraph security semantics.

Notable additions include custom computer-control recognition for high-confidence actions such as click, type, key, drag, screenshot/read-only actions, and page/browser primitives.

Mutating computer-control actions can normalize `computer.control`, `external.write` and `network.external`, while screenshot/read-only paths can retain read authority without being treated as a mutation.

A framework-neutral finding covers mutating computer control without an explicit approval/guardrail.

### OpenAI Agents precision and MCP context

OpenAI Agents support now benefits from:

- exact imported-tool provenance;
- imported MCP server resolution;
- agent clone/runtime MCP binding;
- credential-source reconstruction;
- MCP allow/block filter normalization;
- static identity projection.

Name-only capability inference was also hardened for control/helper functions such as `confirm_*`, `approve_*`, `validate_*`, `verify_*` and `check_*`.

Sensitive authority is no longer inferred from the helper name alone when the body has no corroborating side effect.

## Approval and guardrail semantics

Explicit approvals are now represented as first-class graph controls.

The ADG can project:

- `approval_control` nodes;
- `IMPLEMENTS_CONTROL`;
- `GUARDED_BY`.

Supported semantics include:

- inline/tool-scoped approvals;
- OpenAI preview/confirm gates;
- LangGraph predecessor/interrupt approval gates;
- ADK `HITLToolPlugin(sensitive_tools=[...])`.

ADK generic safety plugins are no longer over-credited as approvals for every privileged action.

Inherited agent-level before-tool/plugin control evidence is carried into effective authority where defensible.

## More precise risk semantics

The public-corpus study drove several changes that reduce misleading authority claims.

### Local container mutation vs external side effect

LangGraph/local container updates are distinguished from externally mutating operations where static call shape allows it.

### Fixed destination vs broad egress

A fixed literal destination is no longer automatically treated as equivalent to arbitrary network egress.

This lets destination-constrained authority remain materially different from open-ended retrieval/egress.

### Session state vs persistent write

State mutation semantics were refined so session/workflow state is not automatically treated as persistent storage authority.

### Richer sensitive mutation domains

The risk model gained clearer semantics for external side effects, destructive writes, and sensitive financial/identity/security mutation domains.

## Offline IAM authority from Terraform

v0.5 adds opt-in cross-repository authority correlation for GCP IAM declared in Terraform.

Example:

```bash
horustrace scan ./agent-app \
  --authority-source ../platform-infra \
  --fail-on high
```

The infrastructure repository must already be checked out locally.

HorusTrace does **not** clone it, authenticate to GitHub, call Google Cloud, or download live IAM bindings.

Supported Terraform IAM evidence is correlated only with application identities already present in the normalized graph.

Matching roles and resource scopes are recorded as **declared authority** with source provenance.

Dynamic HCL principals, IAM conditions, group expansion, role-to-permission expansion, inheritance and out-of-band cloud changes remain unresolved rather than being presented as live/effective cloud state.

## OWASP Top 10 for Agentic Applications 2026

v0.5 adds first-class reporting for the OWASP Top 10 for Agentic Applications 2026.

New surface:

```bash
horustrace owasp .
horustrace owasp . --format json
```

HorusTrace adds conservative ASI mappings to its rule catalogue and exposes OWASP summary data in the dedicated OWASP command, normal JSON scan output, SARIF and console finding labels.

### Runtime-aware OWASP reporting

OWASP reporting also became source-context aware.

Each category can report:

- detector status;
- runtime status;
- total finding count;
- runtime finding count;
- non-runtime finding count;
- unknown-context count;
- source-context distribution;
- triggered rules;
- affected agents;
- runtime-affected agents.

Unknown source context is not treated as non-runtime.

A category with no current deterministic detector remains `NOT ASSESSED` rather than being presented as clean.

A clean mapped-detector result is not represented as proof of full OWASP compliance.

## Framework adapter contract v1

v0.5 formalizes the boundary between framework-specific parsing and the framework-neutral HorusTrace model.

A Python adapter now has an explicit contract:

- stable kebab-case name;
- `detector(Path) -> bool`;
- `scanner(Path) -> Graph`;
- contract version 1;
- static execution model;
- no target-code execution.

The installed built-in catalogue is visible through:

```bash
horustrace adapters
horustrace adapters --format json
```

Automatic loading of arbitrary installed third-party plugins is intentionally outside contract v1. Installing a Python package should not silently expand the HorusTrace execution trust boundary.

## Research-driven precision improvements

A major v0.5 design principle was to improve semantics from frozen public-repository evidence rather than tune for lower finding counts.

### Frozen public study expanded to 90 repositories

The v0.4.1 release had been exercised against a 30-repository public corpus.

After that release, HorusTrace added and froze additional cohorts, building a 90-repository study with exact repository revisions and reproducible static-only runners.

The research harness records agent/tool/MCP/identity counts, ADG nodes and edges, findings, flow paths, reachability, attack paths, resolution gaps, MCP binding telemetry, OWASP summaries and residual unknown evidence.

### Regex `compile` false positive removed

The scanner previously risked treating qualified APIs such as `re.compile(...)` as Python code execution because the leaf call name was `compile`.

v0.5 restricts code-execution inference to actual supported built-in execution constructs such as `compile`, `eval` and `exec`.

The correction was applied both to adapter-level inference and repository-level enrichment.

### Control helper names no longer imply side effects

A helper named, for example, `confirm_slack_publish` is no longer granted `external.write` merely because its name contains `publish`.

Control/helper prefixes require corroborating body-call evidence before privileged authority is added.

### Subprocess payload no longer means executable control

One of the most important flow-precision fixes came from the frozen FastAgent study.

The scanner previously treated every `subprocess.run(...)` argument as capable of controlling process execution.

That created false `secret_value -> process_execute` flows when a secret-derived payload was sent through `input=` to a fixed executable.

v0.5 distinguishes executable/command control, argv/command arguments and shell command strings from configuration/payload fields such as `input=`, stdout/stderr, environment and working directory.

Across the frozen study this removed **73 false process-execution flows**, confined to the two repositories exhibiting that pattern, without removing the six proven agent-reachable flows.

### Proven non-agent contexts no longer require an unrelated agent

CLI/test/application-support context can now establish proven non-agent execution even when the repository has zero normalized agents.

Runtime code without binding evidence remains unknown.

This reduced residual unknown reachability without converting uncertain runtime code to safe/non-agent.

### Residual unknown: ArcadeAI shared auth runtime

The sole residual unknown remains in the pinned `ArcadeAI/arcade-mcp` revision.

The flow is:

```text
httpx.get
  ↓
get_valid_access_token
  ↓
refresh_access_token
  ↓
httpx.post
```

Inbound provenance confirms a real MCP-server runtime path:

```text
MCPServer.__init__
→ _init_arcade_client
→ _load_config_values
→ get_valid_access_token
```

The same authentication utility also has CLI consumers.

HorusTrace therefore preserves `agent_reachability: unknown` rather than forcing an agent or non-agent classification.

The provenance candidate search remains bounded and exposes truncation when the repository contains more inbound roots than the emitted evidence budget.

### Unknown-flow progression

During the frozen study the residual unknown set moved:

```text
32 → 5 → 1
```

Those reductions came from general semantic fixes including subprocess payload versus executable-control modeling, proven execution-context semantics, and stronger provenance/binding evidence.

They did not come from repository-specific suppression or from reclassifying ambiguous runtime behavior as safe.

## Static-first safety model

v0.5 retains the core HorusTrace trust boundary.

Scanning does not require HorusTrace to:

- import target Python modules;
- execute target application code;
- start an agent;
- start an MCP server;
- contact configured MCP endpoints;
- authenticate to production cloud/SaaS systems;
- download live IAM bindings;
- infer runtime effectiveness from configuration presence.

Where evidence is dynamic or missing, HorusTrace reports unresolved coverage or unknown authority.
