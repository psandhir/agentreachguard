# HorusTrace v0.9.0 — Recall Foundation

HorusTrace v0.9 is a discovery-quality release.

The release is driven by the frozen 180-repository Real-World Agent Security Study
2026. Its purpose is to make the Agent Security Graph substantially more complete
before HorusTrace attempts the next major step: provenance-ranked effective-authority
binding.

The governing sequence remains:

> discover correctly → bind correctly → reason correctly → then expand policies.

## What changed

### LangGraph semantic discovery

LangGraph is now modeled as workflow topology rather than treating every registered
node as an agent or tool.

v0.9 adds or strengthens:

- explicit workflow-node representation;
- StateGraph and MessageGraph discovery;
- workflow/control edges;
- standalone LangChain `@tool` and `StructuredTool` discovery;
- model/tool node role classification;
- same-name source declarations kept distinct where provenance differs;
- conservative handling of deterministic transforms and unresolved nodes.

On the frozen cohort:

- LangGraph agent/workflow recall: **0.9613**;
- LangGraph tool recall: **0.9660**.

### Framework-neutral model/tool loops

HorusTrace can now recognize source-proven agent loops outside first-class
frameworks.

A generic root requires evidence linking:

1. model invocation;
2. a tool catalogue exposed to the model;
3. model-selected tool-call handling; and
4. concrete tool dispatch.

A class merely named `Agent`, an LLM call with no model-controlled tools, or a
generic `tools=` keyword is not sufficient.

MCP/custom agent recall on the frozen cohort is now **0.6250**, above the v0.9
release gate of 0.60.

### MCP discovery v2

v0.9 materially expands static MCP discovery across:

- programmatic Python MCP clients and servers;
- stdio, SSE and streamable HTTP;
- custom source-proven MCP wrapper classes;
- OpenAI Agents MCP server definitions;
- Pydantic AI MCP constructs;
- configured remote servers;
- server/tool definitions that exist structurally but are not proven agent-bound.

Unbound MCP entities are visible in topology without fabricating `INVOKES` or
effective-authority relationships.

Explicit MCP-server recall improved from **0.2727** to **0.8636** on the frozen
cohort.

### Repository traversal hardening

A single unreadable path or a repository containing a large unrelated source tree no
longer needs to abort an otherwise useful scan.

v0.9:

- continues across unreadable directories and path-resolution failures;
- avoids directory-symlink recursion and external symlink traversal;
- separates the relevant analysis-candidate limit from a separate total repository
  traversal ceiling;
- preserves coverage diagnostics when evidence cannot be read.

Frozen-cohort scanner execution improved from **179/180** to **180/180**.

### Discovery provenance

Newly discovered generic roots and unbound MCP entities retain additive discovery
metadata so later phases can distinguish why an entity exists from whether an agent
has authority to invoke it.

This release deliberately keeps:

> entity existence != authority.

## Important limitations

v0.9 is not an authority-fidelity release.

Effective-authority precision remains **0.2778**. Authority binding is therefore the
primary scope of v0.10 rather than something this release claims to have solved.

MCP-server precision against completeness-marked locked truth is only **0.0580**.
The release claims the measured MCP recall improvement, not high declaration
precision. Many additional declarations require further reference-completeness
adjudication.

The study also does not establish finding assertion precision/recall, exhaustive
attack-path recall, or runtime exploitability. Finding and attack-path counts should
not be interpreted as validated runtime vulnerabilities.

## Compatibility

- Existing CLI commands remain supported.
- Existing rule IDs remain stable.
- Python 3.11+ remains supported.
- Target applications are still not imported or executed.
- HorusTrace still does not launch MCP servers during static analysis.
- No live cloud credentials or cloud API calls are required for the core scanner.

## Next: v0.10 Authority Fidelity

The next development cycle focuses on proving which discovered relationships are
actual authority relationships.

Priorities:

1. provenance-ranked Agent → Tool / MCP binding;
2. declaration vs advertisement vs dispatch vs effective invocation;
3. deployment/workload identity attribution;
4. authority completeness and unresolved-state certificates;
5. targeted MCP precision/reference adjudication;
6. only then broader policy and attack-path claims.
